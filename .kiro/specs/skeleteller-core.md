## Overview

SkeleTeller is a skeleton for producing a demo of a software project from one
storyboard file. One storyboard produces two outputs:

1. **SkeleTeller Quest** (`apps/demo-game/`): a playable browser game. A character
   walks through areas themed on the project. Each scene is one area.
2. **SkeleTeller Storybook** (`apps/slide-walkthrough/`): an interactive slide
   walkthrough. The viewer pages through the same scenes and clicks hotspots.

The Storybook does not embed or run the demoed project. The Quest is a reskin of
one fixed walk-around engine, never a bespoke game per project.

## Storyboard concept

An ordered list of scenes. Five fixed scene types:

| Type | Game | Slides |
|---|---|---|
| `title` | start area with the project name | title page |
| `feature` | station that opens a capture and caption | page with the capture |
| `callout` | station whose capture has numbered hotspots | page with clickable hotspots |
| `code` | terminal station showing a snippet | page with a code block |
| `outro` | exit area with the closing caption | closing page |

An optional top-level `theme` (palette, mood, avatar, props) reskins the game and
tints the slides. Field definitions live in the schema spec, not here.

## Stack

One web stack for the whole repo, chosen for the lightest option that serves both apps.

- **Storyboard:** YAML, validated by one JSON Schema.
- **Validator, game, slides:** TypeScript and Node, Vite, no UI framework. Ajv and js-yaml in the validator.
- **Game rendering:** Canvas 2D, with DOM for the panel and touch controls.
- **Hosting:** GitHub Pages, built by GitHub Actions.

Why: one language means the game and the slides import the same validator, so the
contract cannot drift. A static build needs no server, which satisfies the
free-for-judges requirement. Python and FFmpeg were dropped with the video app.

## Order of work

1. Specs: schema, intake, demo game, slide walkthrough (all written).
2. Schema implementation: workspace, schema, validator, tests, CLI, sample, hooks.
3. Demo game implementation.
4. Slide walkthrough implementation.
5. Hosting, then dogfood on another project, then the submission recording.

Each spec is committed before its code, in its own commit, so the git history shows
spec-first work.

## Acceptance checks

From `AGENTS.md`:

- [ ] One storyboard produces both outputs with no hand-editing of app code.
- [ ] Editing the storyboard (text, scene order) changes both outputs on rebuild.
- [ ] A demo for a sample project can be produced by following the skeleton README alone.
- [ ] Both apps run from their own folders and from public URLs, and share visibly the same storyboard and scene types.
- [ ] Dogfood: a real demo for another entry, and the submission video is a screen recording of the game and the walkthrough.

## Scope caps

From `AGENTS.md`, restated because they decide what not to build.

- Five fixed scene types. No visual editor, no timeline UI.
- Game: one fixed engine, a chain of areas, one character, walk and interact only.
  No combat, enemies, inventory, puzzles, physics, multiplayer, or procedural levels.
- Storybook: paging, hotspots, progress. No live embedding of the demoed project.
- Captions and narration text only. No voice pipeline.
- No accounts, no hosting service, no saved history.
